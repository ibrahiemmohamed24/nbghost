the problem

It passed on your machine because you ran it out of order.

Jupyter lets you run cells in any order you like. The notebook remembers what you did, not what the file says. Hand it to someone else, and the file's own order is all they have.

Cell 1
print(young_survival_rate)
Cell 2
young_survival_rate = df[df.Age < 18].Survived.mean()

Run 2 then 1 in your kernel and it works fine. Run the file top to bottom, the order it's actually saved in, and cell 1 fails before cell 2 ever runs.

what's shipped

Two checks, each catching a different kind of hidden state.

Both read the .ipynb file as written, no kernel, no execution, and exit non-zero the moment something's wrong, so a pipeline can act on it.

01

check-order

Compares each cell's position in the file against its execution_count. A mismatch means the notebook only worked because someone ran it out of sequence.

nbghost check-order notebook.ipynb
02

check-refs

Parses every cell with Python's own AST and tracks which variable is defined where. A cell using a name that isn't defined until a later cell gets flagged by position.

nbghost check-refs notebook.ipynb
a bug worth keeping

A test passed for the wrong reason, and that hid a real bug.

check-refs walked every name in a cell flat, with no idea of scope. A variable defined inside a function looked identical to one defined at the notebook's top level.

The first import-handling test passed immediately. That felt like confirmation. It wasn't: the function-local case simply hadn't been used anywhere else yet, so there was nothing for the flat walk to get wrong on that test.

A second, adversarial test (a variable local to a function, reused by name at the top level) failed instantly. The flat walk had no concept of "this name doesn't exist out here."

The fix wasn't another special case. It was replacing the flat walk with a scope-aware visitor that simply never descends into a function, lambda, or comprehension body.
